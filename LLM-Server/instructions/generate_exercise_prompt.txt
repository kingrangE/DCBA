# 난이도별 출제 기준
- 난이도 1 (기초): 전공서에서 다루는 핵심 개념 하나의 정의와 목적 또는 작동 원리를 묻는다. 개념명을 질문에 제시한다. 답안은 이 개념이 어떤 현상을 설명하는지 짧은 예나 핵심 조건에 연결한다.
- 난이도 2 (기본): 원인이 확인됐거나 주어진 단서로 명확히 좁힐 수 있는 짧은 실무 상황을 제시한다. 상황에 맞는 구체적인 조치와 그 이유를 묻는다. 답안은 문제의 단서를 사용해 개념과 조치를 연결하고, 필요한 경우 재발 방지 방법도 설명한다.
- 난이도 3 (심화): 요청된 과목의 개념을 진단이나 의사결정에 적용해야 하는 실무 상황을 제시한다. 서비스 목표, 정상 대비 달라진 증상, 원인 후보를 구분할 단서, 조치에 영향을 주는 제약을 포함한다. 처음 확인할 항목과 이유, 후보를 구분할 추가 증거, 결과에 따른 조치와 성공 확인 기준을 묻는다. 답안은 가능한 원인이나 대응 경로를 둘 이상 다루고, 각 조치를 선택하는 조건과 위험을 설명한다. 트래픽이나 용량 수치를 쓸 때는 판단에 필요한 단위와 비교 기준을 함께 제시한다.

# 난이도별 예시
아래 예시는 난이도별로 어떤 판단을 요구하는지 보여준다. 요청받은 과목과 난이도에 맞는 새 문제 하나와 답안 하나를 작성한다.

기초
Q: 스레드 풀은 어떤 역할을 하며, 요청마다 새 스레드를 만드는 방식과 어떻게 다른가요?
A: 스레드 풀은 작업을 기존 워커 스레드에 배정해 스레드 생성 비용을 줄입니다. 워커 수를 제한하면 동시에 실행되는 작업 수도 제한할 수 있습니다. 워커가 모두 바쁠 때 새 작업은 설정에 따라 대기하거나 거절됩니다.

기본
Q: PostgreSQL의 두 주문 처리 경로가 주문 행과 재고 행을 반대 순서로 갱신해 교착 상태가 발생했습니다. DB가 한 트랜잭션을 중단했다면 실패한 요청을 어떻게 처리하고 재발을 줄이겠습니까?
A: 중단된 작업 전체를 안전하게 다시 실행할 수 있는지 확인한 후 트랜잭션 단위로 횟수를 제한해 재시도하겠습니다. 결제처럼 되돌리기 어려운 외부 효과가 있다면 중복 실행을 먼저 막겠습니다. 두 경로에서 같은 순서로 잠금을 획득하도록 변경하고 동시 요청으로 검증하겠습니다.

심화
Q: 배포 뒤 주문 API의 정상 응답 p95는 300ms로 유지되지만 1초 타임아웃이 0.2%에서 5%로 늘었습니다. 요청량은 비슷하고 클라이언트는 연결·응답 타임아웃을 같은 오류로 기록합니다. 중복 주문을 허용할 수 없을 때 어디부터 조사하고, 결과에 따라 어떻게 조치하겠습니까?
A: 실패 요청에서 연결 수립과 응답 대기 중 어느 구간에 시간이 쓰였는지 나눠 보고, 요청 ID로 서버의 수신·처리 기록을 대조하겠습니다. 신규 인스턴스에서 연결 수립 지연이 집중되면 해당 인스턴스로의 라우팅을 줄이고 연결 설정을 점검하겠습니다. 서버는 주문을 처리했지만 응답이 늦다면 서버 처리 지연을 조사하고, 주문 조회나 멱등성 키로 처리 상태를 확인해 재시도로 인한 중복을 막겠습니다. 타임아웃 비율이 평소 수준으로 돌아오고 주문 상태가 일치하는지 보겠습니다.
